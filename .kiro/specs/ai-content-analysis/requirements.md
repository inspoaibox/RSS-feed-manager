# 需求文档

## 简介

本功能为 RSS 订阅管理器新增 AI 智能内容分析能力。用户可以通过自然语言输入查询（如"我想看和 Python 相关的话题"），系统将基于已保存的订阅文章内容进行智能检索和分析，返回 AI 整理的分析结果以及相关文章列表。

## 术语表

- **AI分析系统**: 负责处理用户查询、检索相关文章、生成分析结果的核心模块
- **查询**: 用户输入的自然语言查询文本
- **向量嵌入(Embedding)**: 文本的向量表示，用于语义相似度计算
- **相关度分数**: 文章与查询的匹配程度（0-1之间）
- **分析结果**: AI 生成的分析总结内容
- **相关文章**: 与查询相关的文章列表
- **RAG**: 检索增强生成，先检索相关内容再让AI基于内容生成回答

## 技术方案对比

### 方案一：全文搜索 + AI 总结（最简单）

**技术栈：**
- PostgreSQL 全文搜索 (tsvector/tsquery)
- 现有 AI 服务（OpenAI/Gemini）

**优点：**
- 实现最简单，无需额外依赖
- 不占用额外存储空间
- 可快速上线验证

**缺点：**
- 只能匹配关键词，无法理解语义
- 搜"机器学习"找不到"深度学习"相关文章

**适用场景：** 快速验证、文章数量少（<1000篇）

---

### 方案二：pgvector + OpenAI Embedding（推荐 ⭐）

**技术栈：**
- PostgreSQL + pgvector 扩展（向量存储）
- OpenAI text-embedding-3-small API（生成向量）
- 现有 AI 服务（分析总结）

**优点：**
- 语义搜索，理解用户意图
- 不需要额外部署服务，复用现有 PostgreSQL
- Embedding API 成本极低（$0.02/百万token）
- 备份恢复简单，数据都在一个数据库

**缺点：**
- 需要安装 pgvector 扩展
- 每篇文章增加约 6KB 存储（1536维向量）

**存储估算：**
| 文章数量 | 向量存储空间 |
|---------|-------------|
| 1,000篇 | ~6MB |
| 10,000篇 | ~60MB |
| 100,000篇 | ~600MB |

**适用场景：** 生产环境推荐方案

---

### 方案三：ChromaDB + 本地 Embedding

**技术栈：**
- ChromaDB（嵌入式向量数据库）
- sentence-transformers（本地模型）
- 现有 AI 服务（分析总结）

**优点：**
- 完全离线，无 API 费用
- 语义搜索能力

**缺点：**
- 本地模型占用 90-420MB 磁盘
- 需要额外维护 ChromaDB
- 中文支持不如 OpenAI

**适用场景：** 离线环境、对隐私要求高

---

### 方案四：LangChain/LlamaIndex 框架

**技术栈：**
- LangChain 或 LlamaIndex
- 任意向量数据库
- 任意 LLM

**优点：**
- 功能最全面，支持复杂 RAG 流程
- 社区活跃，文档丰富

**缺点：**
- 框架较重，学习成本高
- 对于简单需求过度设计

**适用场景：** 复杂 AI 应用、需要多轮对话

---

### 方案对比总结

| 方案 | 复杂度 | 语义搜索 | 额外存储 | API成本 | 推荐度 |
|-----|-------|---------|---------|--------|-------|
| 全文搜索 | ⭐ | ❌ | 0 | 仅分析 | 快速验证 |
| pgvector + OpenAI | ⭐⭐ | ✅ | ~6KB/篇 | 极低 | **推荐** |
| ChromaDB + 本地 | ⭐⭐⭐ | ✅ | 模型90MB+ | 0 | 离线场景 |
| LangChain | ⭐⭐⭐⭐ | ✅ | 取决于配置 | 取决于配置 | 复杂场景 |

---

### 推荐方案：pgvector + OpenAI Embedding

**选择理由：**
1. **复用现有架构** - 项目已使用 PostgreSQL，只需添加 pgvector 扩展
2. **成本可控** - Embedding API 极其便宜，10万篇文章约 $1-2
3. **维护简单** - 数据都在一个数据库，备份恢复方便
4. **效果好** - OpenAI Embedding 对中英文支持都很好
5. **可扩展** - 后续可平滑升级到更复杂的 RAG 方案

**实现流程：**
```
用户输入查询 
    → OpenAI 生成查询向量 
    → pgvector 相似度搜索 
    → 获取 Top-K 相关文章 
    → 组装 Prompt 
    → AI 生成分析总结 
    → 返回分析 + 文章列表
```

## 需求列表

### 需求 1：自然语言查询

**用户故事:** 作为用户，我希望能够用自然语言输入查询来搜索我订阅的内容，以便快速找到与特定话题相关的文章。

#### 验收标准

1. 当用户提交查询文本时，AI分析系统应提取关键词并在数据库中搜索相关文章
2. 当AI分析系统搜索文章时，AI分析系统应按相关度分数从高到低排序返回结果
3. 当没有文章匹配查询时，AI分析系统应返回空结果并显示友好提示信息
4. 如果查询文本为空或仅包含空白字符，则AI分析系统应拒绝请求并返回验证错误

### 需求 2：AI 分析生成

**用户故事:** 作为用户，我希望看到 AI 对搜索结果的分析总结，以便快速了解订阅内容中的主要主题和趋势。

#### 验收标准

1. 当找到相关文章时，AI分析系统应基于文章内容生成分析总结
2. 当生成分析时，AI分析系统应按主题组织内容、提取关键点并识别趋势
3. 当未配置 AI 服务商时，AI分析系统应仅返回文章列表而不生成分析
4. 如果 AI API 调用失败，则AI分析系统应返回文章列表并在分析部分显示错误信息

### 需求 3：文章列表展示

**用户故事:** 作为用户，我希望看到相关文章列表及其元数据，以便点击查看原始内容。

#### 验收标准

1. 当显示搜索结果时，AI分析系统应展示文章标题、来源订阅源名称、发布日期和相关度分数
2. 当显示搜索结果时，AI分析系统应包含每篇文章的文本摘要片段
3. 当用户点击文章时，AI分析系统应跳转到文章详情页面
4. 当显示结果时，AI分析系统应限制初始显示为20篇文章并支持分页

### 需求 4：语义搜索（向量检索）

**用户故事:** 作为用户，我希望系统使用语义搜索来查找相关内容，以便即使文章不包含精确的关键词也能找到相关文章。

#### 验收标准

1. 当文章保存到数据库时，AI分析系统应为文章生成并存储向量嵌入
2. 当搜索文章时，AI分析系统应使用向量相似度搜索来查找语义相关的内容
3. 当向量嵌入服务不可用时，AI分析系统应回退到基于关键词的全文搜索
4. 当生成向量嵌入时，AI分析系统应使用已配置的 AI 服务商的嵌入 API

### 需求 5：专属分析页面

**用户故事:** 作为用户，我希望从专门的页面访问 AI 分析功能，以便获得专注的内容发现体验。

#### 验收标准

1. 当用户导航到 AI 分析页面时，AI分析系统应显示搜索输入框和最近的查询记录
2. 当显示分析结果时，AI分析系统应在卡片中展示 AI 总结并支持 Markdown 渲染
3. 当显示分析结果时，AI分析系统应在总结下方展示相关文章列表
4. 当搜索进行中时，AI分析系统应显示加载指示器

### 需求 6：查询历史

**用户故事:** 作为用户，我希望保存并重新访问我的分析查询，以便跟踪我长期感兴趣的话题。

#### 验收标准

1. 当用户提交查询时，AI分析系统应将查询保存到用户的历史记录中
2. 当显示 AI 分析页面时，AI分析系统应展示用户最近的查询记录（最多10条）
3. 当用户点击已保存的查询时，AI分析系统应使用该查询重新执行搜索
4. 当用户删除已保存的查询时，AI分析系统应从历史记录中移除它

### 需求 7：向量嵌入配置

**用户故事:** 作为系统管理员，我希望配置向量嵌入生成设置，以便控制资源使用和成本。

#### 验收标准

1. 当配置系统时，AI分析系统应允许选择使用 API 或本地模型生成向量嵌入
2. 当使用 API 生成向量嵌入时，AI分析系统应使用用户已配置的 AI 服务商
3. 当文章的向量嵌入生成失败时，AI分析系统应记录错误并继续存储文章而不阻塞
4. 当向量嵌入列为空时，AI分析系统应在向量搜索中排除该文章但在关键词搜索回退中包含它
